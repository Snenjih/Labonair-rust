# Default Platform Action Requirements Register

**Status:** Static action/binding inventory complete for default macOS, Linux, and Windows profiles; semantics and runtime acceptance remain open
**Baseline:** Zed commit `3569541038dd51524b03998ba4d38d253cb54f80`
**First acceptance platform:** macOS
**Owner:** Product architecture with each canonical capability owner

## Inventory scope and evidence

The three default operating-system profiles contain 930 active macOS bindings
across 133 context blocks, 931 Linux bindings across 130 blocks, and 870
Windows bindings across 129 blocks. They reference 585, 561, and 557 distinct
action names respectively; their union is 595, with 546 names common to all
three. Ten actions bound on Linux and/or Windows are not bound in the macOS
default. All 2,731 active binding records and four explicit null entries are
listed below. Binding presence is static inventory evidence only.

The pinned Linux runtime dump records 1,404 registered action names. Of the
595 identifiers in the three default maps, 590 match a registered name directly
and five are declared deprecated aliases. Resolving those aliases reaches 591
unique registered actions; the other 813 registered Linux actions have no key
binding in any of these three defaults and receive stable IDs in
[`registered-actions-unbound.md`](registered-actions-unbound.md). These counts
do not establish command-palette, menu, pointer, extension, or programmatic
reachability. Linux registration does not establish macOS registration.

Each action name has one requirement ID. The 585 macOS IDs retain their existing
`ACT-MACOS-<namespace>-<action>` values. The ten additional actions use
`ACT-PLATFORM-<namespace>-<action>`. Each profile cell records its exact default
key sequences, activation context, and any action arguments.

Five names in the default maps are deprecated aliases in the pinned Linux
runtime metadata. They resolve to three registered action names:

The seven macOS base-profile overlays (Atom, Cursor, Emacs, JetBrains, Sublime
Text, TextMate, and VS Code), the conditional Vim/Helix layer, and the
macOS-specific override layer now have stable per-binding IDs in

default macOS file has 585 action identifiers; its specific override layer adds

profiles or modes. Static map records do not prove action semantics or runtime
dispatch. The six shared non-macOS profile overlays and common Linux/Windows
override layer now have 446 stable binding IDs in
[`keymap-nonmacos-requirements.md`](keymap-nonmacos-requirements.md); that
register also records 259 default Linux/Windows key-equivalent block IDs.
Static coverage does not establish Linux or Windows dispatch. User-authored
bindings and profile-selection/reload behavior remain open.

## Shared acceptance contract inherited by every action

- **User goal and flow:** Observe the action in the pinned runtime, describe its
  user-visible effect independently, then verify `key sequence → active
  context → owning operation → visible/stateful result`. Action-specific
  semantics are `Pending` until observed and written per requirement.
- **States:** Record applicable active/inactive context, available/unavailable,
  normal, empty, loading, error, cancelled, and recovery states. Mark states
  `N/A` only with a reason. Exact per-action state sets remain `Pending`.
- **Keyboard and mouse:** Verify every listed sequence, repeat/timeout behavior,
  context exclusion, keyboard discoverability, and each runtime-provided menu
  or pointer route. Pointer behavior remains `Pending` until observed.
- **Settings and persistence:** Verify profile selection and user/project
  overrides, validation, conflicts, save/reload, reset, and migration. Record
  domain setting effects only after observation. These details remain `Pending`
  per action.
- **Owner and dependencies:** Assign one canonical Labonair capability owner,
  its public typed command/action contract, and dependencies. The workflow
  family is a routing hint, not an owner assignment. All exact assignments
  remain `Pending`.
- **Acceptance evidence:** Record the pinned and Labonair build, OS/window,
  profile, active/inactive context, input sequence, visible result, failure or
  cancellation path, and artifact/test link. Runtime evidence remains `Pending`.
